# MD→HTML via the uni-md2html tool — Design

**Date:** 2026-06-12
**Branch:** `feat/md-html-uni-converter`
**Base:** `personal` (fork main-equivalent; contains the on-demand MD→HTML feature `6b48cbe99`)

## Goal

When the file viewer renders a markdown report as HTML, produce the **UniUni-branded
report** generated by the user's `uni-md2html` tool
(`/Users/longngo/src/uni/md-html-converer/`) instead of the current plain in-process
`marked` render. The branded output gives the report masthead, Poppins/Manrope
typography, peach-zebra tables, and raw-mermaid support — the same artifact the user
gets when converting reports by hand.

The conversion must stay robust: if the tool is unavailable (not installed, not on
`PATH`, errors out), the viewer must still render via the existing `marked` path
rather than break.

## Background

Today `WorkspaceFileSystem.readFileAsHtml` (server) reads a markdown file, calls the
synchronous in-process `renderMarkdownDocument(contents)` (`marked` → a light-themed
standalone document), and caches the result in a per-process LRU keyed by resolved
path + content hash. The RPC `projects.renderMarkdownHtml` returns that HTML; the web
file viewer displays it in a **sandboxed iframe (`allow-scripts allow-popups`)**.

Two facts make the swap feasible:
- `uni_md2html.converter` exposes `convert_text(text, opts) -> str`, but the installed
  **console script is file-based** (reads file paths, writes `.html`). Per the chosen
  resolution strategy (PATH default `uni-md2html`), we drive the **file-based CLI** via
  a temp-file round-trip — works with whatever command resolves, no Python-internals
  coupling.
- The viewer iframe already allows scripts, so the branded output's mermaid
  `<script type="module">` and the Google-Fonts/mermaid CDN links run as-is. No viewer
  change is required.

## Decisions (settled with the user)

| Question | Choice |
|----------|--------|
| Tool resolution | **Env var + PATH default** — `T3CODE_MD2HTML_CMD` if set, else `uni-md2html` on `PATH`. |
| Fallback when tool unavailable/fails | **Fall back to the current `marked` renderer.** Viewer always works. |
| Theme / offline | **`report` theme, with CDN fonts** (no `--self-contained`). |

## Approach

Introduce a small server service `MarkdownHtmlRenderer` that owns "markdown string →
standalone HTML string", and have `WorkspaceFileSystem` depend on it instead of
importing `renderMarkdownDocument` directly. The LRU cache stays in
`WorkspaceFileSystem` unchanged — it caches the final HTML regardless of which renderer
produced it.

### `MarkdownHtmlRenderer` (`apps/server/src/workspace/markdownHtmlRenderer.ts`)

Shape:

```ts
interface MarkdownHtmlRendererShape {
  readonly render: (markdown: string) => Effect.Effect<string>; // never fails
}
```

`render(markdown)`:

1. Resolve the command: `process.env.T3CODE_MD2HTML_CMD?.trim() || "uni-md2html"`.
   A single executable path/name (e.g. set it to
   `…/md-html-converer/.venv/bin/uni-md2html` to use the dev venv with no install).
2. `Effect.scoped`:
   - `fileSystem.makeTempDirectoryScoped({ prefix: "t3code-md2html-" })` (auto-removed
     on scope close, success or failure).
   - write `<tmp>/in.md` ← markdown.
   - `processRunner.run({ command, args: ["<tmp>/in.md", "--theme", "report", "-o", "<tmp>/out.html"], timeout: "30 seconds", outputMode: "truncate" })`.
     `outputMode: "truncate"` because stdout/stderr are irrelevant (we read the output
     *file*) — a chatty tool must never trip `ProcessOutputLimitError`.
   - on exit code `0` **and** a non-empty `<tmp>/out.html`, return the file contents.
3. **Fallback** to `renderMarkdownDocument(markdown)` via a single blanket
   `Effect.catchAll` over the whole scoped round-trip — the failure channel is the full
   `ProcessRunError` union (`ProcessSpawnError | ProcessStdinError |
   ProcessOutputLimitError | ProcessReadError | ProcessTimeoutError`) plus
   `PlatformError` from the temp-file IO, so we catch the *union*, not named tags. We
   additionally treat these *value*-channel results as fallback triggers: non-zero /
   null `code`, `timedOut`, and a missing or whitespace-only output file. Log at debug
   level so a misconfigured command is diagnosable without spamming. `render` therefore
   has error type `never`.

The service depends on `ProcessRunner`, `FileSystem`, and `Path`.

### Wiring

- `WorkspaceFileSystem.readFileAsHtml`: replace `const html = renderMarkdownDocument(contents)`
  with `const html = yield* renderer.render(contents)`. Everything else (path
  resolution, 2 MB read cap, stat/hash cache) is unchanged. The call already runs inside
  an `Effect.fn` generator, so `yield*`-ing an async render is natural.
- `makeWorkspaceFileSystem`: `const renderer = yield* MarkdownHtmlRenderer`.
- Layer graph (`server.ts`): `WorkspaceFileSystemLayerLive` gains
  `Layer.provide(MarkdownHtmlRendererLive)`, and the renderer layer is
  `Layer.provide(ProcessRunner.layer)`. `ChildProcessSpawner`, `FileSystem`, `Path` come
  from the platform layer (Bun/Node services) already at the root, exactly as
  `TerminalManagerLive` already does for `ProcessRunner`.

### Why a temp-file round-trip (not stdin)

The resolved command is the file-based console script; it has no stdin mode. A
temp-file round-trip works with any command that behaves like the CLI and avoids
coupling to Python internals or to a specific interpreter invocation. Smoke-tested:
`uni-md2html in.md --theme report -o out.html` → exit 0, valid branded doc, mermaid
`<div class="mermaid">` preserved, CDN font links present (5.9 KB for a trivial doc).

## Alternatives considered

- **Call `convert_text` via `python -c` over stdin/stdout.** Avoids temp files, but
  contradicts the chosen PATH-default resolution (the default `uni-md2html` is the
  file-based script, not a Python entrypoint) and couples us to the package's import
  path + a Python interpreter. Rejected.
- **Add a `--stdin`/`-` mode to uni-md2html, then pipe.** Cleaner runtime, but edits a
  *separate repo* — cross-repo coupling and scope creep for a t3code feature. Rejected
  (could be a future enhancement that lets us drop the temp files).
- **Port the tool's theme/CSS/slug/mermaid logic to TypeScript (in-process).** No Python
  dependency, synchronous, fastest. But duplicates a non-trivial, evolving tool and
  guarantees drift from the canonical output the user wants. Defeats "use this tool."
  Rejected.
- **Hard dependency, no fallback.** Rejected per the user's choice — the viewer must
  degrade gracefully where the tool isn't installed.
- **`--self-contained` (offline fonts).** Rejected per the user's choice — exact
  typography via CDN fonts is preferred; the iframe has network access.

## Tradeoffs & known limitations

- **Latency:** an uncached render now spawns a Python process (~100–300 ms cold) instead
  of an in-process call. Mitigated by the existing LRU (repeat views are free) and the
  on-demand, user-initiated nature of the viewer. A 30 s timeout bounds the worst case.
- **Determinism in tests/CI:** wherever `uni-md2html` isn't installed, output is the
  `marked` fallback. The existing `readFileAsHtml` tests assert the fallback shape, so
  they stay green; the new renderer test drives the tool path with a *stub*
  `ProcessRunner`, so it doesn't depend on a real install.
- **Branded output differs from the old plain doc** — by design. Intra-report link
  navigation still works (the viewer's link interceptor is renderer-agnostic).
- **Cached fallback is sticky.** The LRU caches whatever `render` produced. If the tool
  is *transiently* unavailable, the fallback HTML is cached and pinned until the file's
  content changes or the process restarts — a later install/fix won't retroactively
  re-render it. Caching the fallback is deliberate: for the common "tool not installed"
  case it avoids re-spawning a doomed subprocess on every view. Distinguishing transient
  from permanent failure (TTL / no-cache-on-fallback) was judged not worth the
  complexity; the command resolves once at layer construction.
- **Env var is a single executable**, not a command line. Setting `python -m uni_md2html`
  is not supported; point it at the console-script path instead. Documented in the var's
  doc comment.
