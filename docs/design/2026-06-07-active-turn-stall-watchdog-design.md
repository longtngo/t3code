# Active-turn stall watchdog — design

**Date:** 2026-06-07
**Author:** Claude (build-task)
**RCA:** `~/reports/t3code/2026-06/2026-06-07-parallel-subagent-turn-hang-rca.md`

## Goal

When the provider (Claude Agent SDK) subprocess silently stalls in the middle of an
active turn — emitting no further events and never closing the turn — t3code currently
believes the thread is "running" forever. Neither safety net recovers it:

- `maybeWakeThreadForCompletedTask` only wakes **idle / turn-less** threads.
- `ProviderSessionReaper` explicitly **skips any session with `activeTurnId != null`**, so a
  stalled turn keeps its session alive indefinitely (observed: 6h51m).

The only recovery today is a manual user message. This watchdog detects an active turn that
has gone silent past a threshold and **recovers it automatically** (and surfaces it), so the
user is no longer required to babysit.

## Verified facts driving the design

1. **`lastSeenAt` is not a usable activity clock.** It is bumped only in `ProviderSessionDirectory.upsert`,
   called from `startSession` / `sendTurn` / `stopSession` / `stopAll` (`ProviderService.ts:597,661,830,1008`)
   — i.e. on turn _start_, never per event. A healthy long turn has a stale `lastSeenAt`.
   → The watchdog needs its own "last SDK event" clock.
2. **`account.usage.updated` is generated by t3code, not the SDK** (60 s poller in
   `ClaudeAdapter.ts:1266-1321`, runs at adapter scope, independent of the SDK process).
   It is the _only_ non-SDK runtime event. → It must be **excluded** from the stall clock, else a
   healthy poll would mask a dead SDK.
3. **Recovery primitives exist:**
   - `thread.turn.interrupt` → `ProviderCommandReactor.processTurnInterruptRequested` →
     `providerService.interruptTurn` (graceful; depends on the SDK responding).
   - `thread.session.stop` → reactor stops the session **and** dispatches `thread.session.set`
     with `activeTurnId: null` (forceful; does not depend on the SDK responding).
   - `thread.turn.start` with a synthetic user message → resumes the SDK session
     (`session.started{resume:<sdkSessionId>}`). This is exactly what the manual "Continue" did at
     recovery time (verified in the provider log).
4. **The stall signature is precise** (from the log): the last SDK events before the freeze were
   terminal (`task.completed` + `item.completed` for the parallel `collab_agent_tool_call`s) — the
   ball was in the model's court to issue the next inference, and it never did. A turn that is
   legitimately waiting on a _foreground tool_ instead has its last event be `item.started` /
   `item.updated` (tool in flight). This distinction is the core false-positive guard.

## Approach

Two cooperating pieces plus config:

### 1. `TurnActivityTracker` (new in-memory service)

A tiny service wrapping a `Ref<HashMap<ThreadId, TurnActivity>>` where
`TurnActivity = { turnId: TurnId; lastEventAt: number; lastEventType: string }`.

- **Writer:** `ProviderRuntimeIngestion.processRuntimeEvent` records every SDK-originated event:
  on `turn.started` it (re)initialises the entry for the new turn; on any other event with a
  matching/!present turn it updates `lastEventAt`/`lastEventType`; on `turn.completed` /
  `session.exited` it clears the entry.
  **Excluded event types (do not refresh the clock):** `account.usage.updated`,
  `account.rate-limits.updated` (the only non-SDK events).
- **Reader:** the watchdog sweep.

Rationale for a dedicated tracker rather than reusing the projection: the projection's
`account.usage` activity upserts in place on every poll (its `createdAt` advances), which would
defeat detection; and an in-memory Ref is O(1) per event vs a per-sweep projection query.

### 2. `ProviderTurnStallWatchdog` (new layer, modeled on `ProviderSessionReaper`)

A forked, scheduled sweep (`Schedule.spaced`, default every 60 s). For each tracked thread:

**Trip conditions (all must hold):**

- thread resolves and `thread.session?.activeTurnId != null` (active turn) and
  `thread.session.status === "running"`;
- `thread.archivedAt === null`, `!thread.hasPendingApprovals`, `!thread.hasPendingUserInput`
  (not legitimately blocked on the user);
- `now - lastEventAt >= stallThresholdMs`;
- `lastEventType` is **not** an "in-flight" type — i.e. not in `{ "item.started", "item.updated" }`
  (the SDK is legitimately waiting on a running tool, not stalled). All terminal/continue-expected
  types (`item.completed`, `task.completed`, `content.delta`, `turn.proposed.completed`, …) are
  eligible.

**On trip:**

1. **Always surface.** Append a `runtime.warning` thread activity ("No provider activity for Xm on
   an active turn — attempting recovery") so it shows in the work log, and (reusing existing
   thread-notification infra) the user gets an OS notification.
2. **Recover (gated by `stallRecovery` setting; default `"auto"`).**
   - First attempt: dispatch `thread.turn.interrupt` (graceful). Record attempt #1 against the turnId.
   - If a later sweep finds the **same turnId** still active and still silent (interrupt didn't take —
     SDK wedged): escalate to `thread.session.stop` **then** `thread.turn.start` with a synthetic
     "Continue the work that was interrupted; the previous turn stalled." message (forceful resume).
   - **Attempt cap:** at most 2 recovery attempts per `turnId`. After the cap, append a
     `runtime.error` activity ("automatic stall recovery exhausted — manual continue needed") and
     stop acting on that turn (no loop). The cap is keyed on turnId so a fresh turn resets it.
   - Setting `stallRecovery: "surface-only"` performs step 1 only (no interrupt/stop), for users who
     want alerting without automatic intervention.

### Config (env + server settings, mirroring reaper/STRICT-guard patterns)

- `stallThresholdMs` — default **900_000 (15 min)**. Conservative: SDK streams thinking-tokens,
  content, and tool/task lifecycle frequently during real work, and subagents emit periodic
  `task.progress`; 15 min of _total_ SDK silence on a turn whose last event was terminal is a
  near-certain stall. Overridable via `T3CODE_TURN_STALL_THRESHOLD_MS`.
- `sweepIntervalMs` — default **60_000**.
- `stallRecovery` — `"auto" | "surface-only" | "off"`; default `"auto"`. Env
  `T3CODE_TURN_STALL_RECOVERY`. `"off"` disables the watchdog entirely.

## Why this is safe against false positives

- The in-flight-tool guard (`lastEventType ∉ {item.started,item.updated}`) excludes the one
  legitimate "SDK silent while a foreground tool runs" case.
- Pending-approval / pending-user-input threads are excluded (the SDK is correctly waiting on a human).
- `task.progress` from a running subagent refreshes the clock, so long subagents don't trip.
- 15 min threshold + terminal-last-event makes a false trip require: an active turn, last event
  terminal, no pending tool/approval/input, and zero SDK output for 15 min — which is the stall
  itself. The graceful interrupt-first escalation further limits blast radius (an interrupt of a
  truly-still-working turn would surface as a normal interruption, recoverable by the user).

## Alternatives considered

- **Extend `ProviderSessionReaper` to reap active turns past a larger threshold.** Rejected: the
  reaper's clock (`lastSeenAt`) is the wrong signal (turn-start time, not activity), and "reap"
  (stopSession) loses the turn without resuming it. The watchdog needs a different clock and a
  recover-not-kill action. Keeping them separate keeps the reaper's idle-session semantics intact.
- **Drive detection from the projection's last-activity timestamp.** Rejected: the `account.usage`
  activity upserts in place each poll, advancing its timestamp and masking SDK silence; also heavier.
- **Trip purely on a timeout with no last-event-type guard.** Rejected: false-trips legitimately
  long foreground tools (e.g. a 20-min Bash with no streaming).
- **Surface-only, never auto-recover.** Rejected as the _default_ (the project already auto-wakes in
  the idle case, and the user's pain is babysitting), but retained as the `surface-only` setting.

## Tradeoffs / limitations

- Detection is heuristic; an adversarial workload (15 min+ of intentional foreground silence with a
  terminal last event) could trip. Mitigated by graceful-interrupt-first and the `surface-only`/`off`
  settings.
- Recovery re-issues a turn, costing tokens; the attempt cap bounds this to ≤2 per turn.
- This is a defensive workaround for an **upstream SDK bug** (parallel-subagent continuation stall);
  see item 2 (SDK floor + bug doc). If/when the SDK fixes it, the watchdog remains as a generic
  safety net.

## Follow-ups deferred

- A UI affordance ("turn stalled — Continue?") button distinct from the OS notification.
- Telemetry counter for stall trips / recovery outcomes to tune the threshold from real data.
- `surface-only` mode (alert without intervening) — needs bespoke notification plumbing since the
  OS notification otherwise rides the recovery's terminal-state edge.
- Graceful `thread.turn.interrupt`-first escalation before the forceful stop.

## Revised v1 scope (after design review — 2026-06-07)

Two adversarial reviews (correctness/race + simplicity) converged on a smaller, safer v1. Changes
from the draft above:

**Simplification (accepted):**

- **No dedicated `TurnActivityTracker` service/layer.** Fold the last-event clock into
  `ProviderRuntimeIngestion` (it is already the per-event writer with `event.createdAt` and
  `activeTurnId`/`eventTurnId` in hand). Add a `Ref<HashMap<ThreadId, TurnActivity>>` inside its
  `make`, written at the top of `processRuntimeEvent`, and expose one read accessor
  (`listTurnActivity`) on `ProviderRuntimeIngestionShape`. Net: 0 new tracker files.
- **No `ServerSettings` knobs / no contract changes.** Mirror `ProviderSessionReaper`: module-level
  `DEFAULT_STALL_THRESHOLD_MS` (900_000) + `DEFAULT_SWEEP_INTERVAL_MS` (60_000) consts and a
  `…LiveOptions` interface. Overrides via env only: `T3CODE_TURN_STALL_THRESHOLD_MS`,
  and `T3CODE_TURN_STALL_WATCHDOG=0` to disable (layer simply not started).
- **No three-way `stallRecovery` mode.** v1 always auto-recovers (matching the no-opt-out
  `maybeWakeThreadForCompletedTask` precedent); the env kill-switch is the only control.
- **Single forceful recovery, no graceful-interrupt step.** The wedged-SDK case is exactly when
  `interrupt` (which needs the SDK to respond) won't work, so go straight to the forceful path.
- **No server-side notification wiring.** OS notifications are client-side and fire on the
  `running → terminal` turn-state edge; the forceful recovery produces that edge for free. Surfacing
  in v1 = append one `runtime.warning` thread activity via the existing
  `thread.activity.append` dispatch.

**Correctness fixes (accepted, folded into the recovery state machine):**

- **`turn.start` queues behind an active turn** — it does not interrupt it. So recovery is
  **two-phase across sweeps**: sweep N dispatches `thread.session.stop`; once a later sweep observes
  the session `stopped` / `activeTurnId === null`, it dispatches `thread.turn.start` (resume). This
  guarantees the synthetic continue isn't silently queued behind the dead turn.
- **Attempt cap is per-thread, not per-turnId** (a forceful stop+resume mints a new turnId, so a
  per-turnId cap would never accumulate and could loop forever). Cap = 3 recoveries/thread; on
  exhaustion append a `runtime.error` activity and stop acting until the thread completes a turn
  normally. Recovery/attempt state is cleared when the thread has no active turn and no tracker entry
  (i.e. a clean completion).
- **Exclude synthetic turns** (`raw.method === "claude/synthetic-turn-start"`, captured into the
  tracker entry at `turn.started`) from recovery — resuming a background synthetic turn with a
  user-visible "Continue" is wrong.
- **Clear the tracker on `turn.completed` / `session.exited` / `turn.aborted`** (ThreadId-keyed so a
  turnId-less completion still clears), plus a TTL/no-active-turn backstop against leaks.
- **Guard against transition races:** only trip when the tracker entry's `turnId` equals the
  projection's `activeTurnId` (skip "in transition").
- **Wrap recovery dispatches in `Effect.timeout` + `catchCause`** so a wedged subprocess can't also
  wedge the watchdog fiber.

**Refined trip predicate (v1):** active turn (`activeTurnId != null` && `status === "running"`),
tracker `turnId === activeTurnId`, not synthetic, not archived, no pending approvals/user-input,
`now - lastEventAt >= stallThresholdMs`, and `lastEventType ∉ {item.started, item.updated}`
(in-flight tool guard). `runtime.thinking-tokens` / `thread.token-usage.updated` are _not_ excluded,
so they refresh the clock and a long "thinking" gap won't false-trip.

**Revised files touched:** `ProviderRuntimeIngestion.ts` (+ its `Services/` shape for the accessor),
new `provider/Services/ProviderTurnStallWatchdog.ts` + `provider/Layers/ProviderTurnStallWatchdog.ts`,
`server.ts` (layer) + `serverRuntimeStartup.ts` (start), and tests. No `serverSettings.ts`, no
contract changes, no new tracker files.
